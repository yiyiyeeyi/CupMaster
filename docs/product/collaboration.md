# 多 AI 協作流程（Codex × Claude）

> CupMaster 由使用者與兩個 AI 協作開發。兩者角色可以互換：**一方開發、另一方審查**。
> 兩者都能讀寫 Notion。本檔規定交接方式，避免重複爭論或彼此覆蓋。

## 1. 角色

| 角色 | 職責 |
|---|---|
| 使用者 | 產品負責人。決定範圍、流程、優先順序；批准 commit 與流程變更 |
| 開發者（Codex 或 Claude） | 依一條 Notion 需求實作，交付後提交審查 |
| 審查者（另一方） | 依驗收條件與本檔清單檢查，回報問題，不直接改開發者正在做的檔案 |

產品討論可以在任一方進行，但**產品決策只有使用者能定案**，定案後依 `docs/product/product-decisions.md` 第 8 節更新。

## 2. 開工前

1. 讀 `AGENTS.md`、`docs/product/product-decisions.md`、該需求的 Notion 頁面與相關 `docs/`。
2. 確認需求屬於哪個 vertical slice、會不會改變產品流程。改變流程需使用者明確同意。
3. 先提出計畫給使用者確認，再動手。
4. Notion 需求狀態改為「開發中」。

## 3. 交付時（開發者）

在回報中、也在 Notion 該需求頁面附上交接紀錄：

```
需求：REQ-n 標題
分支 / 範圍：改了哪些檔案（新增／修改）
做了什麼：一到三句
如何驗證：lint / typecheck / test / build 結果；手動驗證步驟
驗收條件對照：逐條標 ✅ / ❌ / 無法驗證（說明原因）
已知限制與風險：
需要審查者特別看的地方：
```

Notion 狀態改為「驗收中」。**不要自行 commit 或 push**，等使用者指示。

## 4. 審查清單（審查者）

- [ ] 驗收條件逐條驗證，不只看開發者的自評
- [ ] 沒有違反 `AGENTS.md` 不變式：Bean／器材不是開始沖煮前提；回饋／AI 不是儲存前提；Snapshot 不可變；不捏造量測值；金鑰不在 `NEXT_PUBLIC_*`
- [ ] 沒有超出範圍：沒有順手改產品流程、沒有重新設計版面、沒有做 V1.5／V2 的東西
- [ ] 視覺失敗時，計時、手動沖煮、儲存仍可用
- [ ] 私有影像資料沒有進 git；沒有開啟 session-014、005–010
- [ ] A／B 座標合約兩邊都沒被改
- [ ] lint、typecheck、test、build 自己重跑一次
- [ ] 新邏輯有測試；錯誤與失敗路徑有處理
- [ ] 文件有跟著更新（routes、vertical-slices 等）

審查結果：

```
審查：REQ-n
結論：通過 / 需修改 / 需使用者決定
問題：依嚴重度列出，每條附檔案與行號、重現方式
建議：
```

通過 → 交使用者決定是否 commit，Notion 改「完成」。需修改 → 退回開發者，Notion 維持「驗收中」並附上審查紀錄。

## 5. 避免衝突

- 同一時間只有一方改同一批檔案。平行工作時先說好各自範圍。
- 不使用 reset、clean、restore、stash、checkout 等會丟掉他人工作的指令。
- 研究實驗（`scripts/vision`、`docs/vision`）與產品開發（`src/`）可以平行，但 commit 要分開。
- 對方留下的未提交檔案一律視為有效工作。
